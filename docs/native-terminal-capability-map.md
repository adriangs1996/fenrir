# Native Terminal Capability Map

This document maps current Fenrir capabilities to future native terminal
emulator responsibilities. It is readiness documentation only: it does not
implement a native terminal emulator, change the server language, or replace
current web/Electron behavior.

## Boundary Rule

Keep terminal lifecycle and user intent on the WebSocket control plane, and keep
terminal byte streams behind an explicit data-plane boundary. Do not route raw
terminal bytes through orchestration/projector workflows unless that boundary is
added deliberately.

## Near-Term Adapter Shape

Future native terminal work should start with a narrow adapter boundary, not a
UI rewrite:

- Control plane: keep `TerminalOpenInput`, `TerminalWriteInput`,
  `TerminalResizeInput`, `TerminalCloseInput`, `TmuxAttachInput`, and related WS
  RPCs as the stable server-facing API.
- Data plane: define a transport boundary for high-volume terminal frames/bytes
  before moving rendering out of xterm. Use managed-process log streaming as a
  reference for backfill plus live chunks, but do not reuse its domain model.
- Backend selection: prefer tmux when available, fall back through `PtyAdapter`
  and node-pty/direct execution when not.
- Client shells: keep web and Electron compatibility while introducing native
  shell bridges feature-by-feature.

## Non-Goals For This Task

- No native terminal emulator implementation.
- No Fenrir server rewrite.
- No removal of xterm, Electron IPC, tmux, node-pty fallback, workflows, managed
  processes, remote controller, Browser Lab, Traffic Lens, or Neovim behavior.
