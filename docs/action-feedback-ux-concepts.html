Minimal structural change: the terminal remains the source of visible output, but every action creates an explicit run bar, terminal markers, action history, and recovery actions. Best if you want to keep the existing mental model.

RunningButton spinner and run bar

Action button changes immediately, terminal opens to the owning session, and run duration increments.

SuccessExit code 0 is explicit

Green terminal marker, success toast, and recent history item with duration and copy output action.

FailureExit code and tail output

Failure run bar stays visible until dismissed; retry and copy output remain one click away.

QueuedBusy terminal handling

User can wait, run in a new terminal, or cancel queue entry before shell write happens.

Needs inputPlaceholder guard

Alt-click or first run opens inputs; command is not written until required values are present.

CancelledStop is visible

Shows whether Fenrir killed a subprocess, sent Ctrl-C, or only removed a queued item.

Primary flow

  • Click action or keybinding.
  • Create run id before touching terminal.
  • Open correct terminal route.
  • Write wrapped command and show run bar.

Failure flow

  • Open/write failure shows toast and run card.
  • Exit nonzero pins failed bar.
  • Retry reuses same cwd/env unless edited.
  • Copy error includes command and tail output.

Busy terminal

  • If active terminal is busy, default to new terminal or explicit queue.
  • Queue order is visible in dropdown.
  • User can promote queued run to new terminal.

Tradeoff

  • Lowest UI disruption.
  • Still assumes users inspect terminal output.
  • Needs action-run sentinels for reliable success.

Completed cards collapse by default after a timeout. Failed cards remain expanded until viewed.

Agent context

The card can be attached to the next message as a terminal context without selecting terminal text.

Noise control

Only user-triggered actions become timeline cards. Background terminal activity stays in terminal.

Primary flow

  • Click action.
  • Timeline card inserted immediately.
  • Terminal opens only when requested.
  • Card updates through terminal lifecycle events.

Agent handoff

  • User can click "Ask agent to fix".
  • Run output is attached as context.
  • Agent sees command, cwd, exit code, and tail output.

Edge cases

  • If write fails, card becomes failed before command output exists.
  • If reconnect happens, card shows "reconnecting" until run status resolves.

Tradeoff

  • Excellent audit trail.
  • Can clutter chat if actions are frequent.
  • Needs good collapse defaults.

4. Queue Popover

Actions behave like a compact job queue anchored to the top bar. This makes it clear when a command is waiting, what terminal it will use, and how to reroute it without committing to a permanent side panel.

CancelledBefore vs after start

Before start removes job. After start sends interrupt and records partial output.

Primary flow

  • Click action.
  • If terminal idle, start.
  • If busy, queue popover opens.
  • User chooses wait or new terminal.

Keyboard flow

  • Shortcut can enqueue silently.
  • Top bar badge shows active/failed count.
  • Second shortcut opens queue popover.

Edge cases

  • Terminal closes while queued: reroute prompt appears.
  • Command spawn fails: queue item becomes failed.
  • Reconnect restores queue from server state.

Tradeoff

  • Great for concurrency.
  • Less obvious after popover closes.
  • Needs precise queue semantics.

Primary flow

  • Command strip owns lifecycle.
  • Output markers bracket command output.

Power controls

  • Recent runs, queue, metadata, routes are terminal subtabs.
  • Ctrl-C and cancel are separate controls.
  • Attach output to chat is one click.

Edge cases

  • Interactive command can stay in terminal with HUD state "waiting for shell input".
  • Terminal close prompts to keep or kill active run.

Tradeoff

  • Fast and dense for terminal users.
  • Less discoverable for non-terminal users.
  • Still terminal-centric.
